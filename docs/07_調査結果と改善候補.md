# 調査結果と改善候補

## 調査結果サマリー

- React、Vite、`package.json`、`src/`、`public/` は確認できない
- GitHub Actionsは確認できない
- Firebase Realtime Database REST APIを使用
- localStorageで進行状態を保存
- 画像、音声、動画を静的アセットとして配信
- `.gitignore` で `assets/audio/bk/`、`assets/images/bk/` は除外済み

## 改善候補一覧

| 優先度 | 対象ファイル | 該当箇所 | 現在の状態 | 想定される問題 | 改善案 |
| --- | --- | --- | --- | --- | --- |
| 高 | `firebaseConfig.js` | Firebase設定 | Realtime Database URLをフロントで参照 | 公開DBへの不正書き込みリスク | Firebaseルールをイベント期間・入力形式に合わせて厳格化 |
| 高 | `script.js` | `reserveRemoteLotteryEntry` | クライアント側で抽選番号を予約 | 完全な原子的採番ではない可能性 | Cloud FunctionsまたはRTDB transaction相当の採番方式を検討 |
| 高 | `script.js` | localStorage使用箇所 | `localStorage` 例外の包括対策は限定的 | プライベートモード等で例外発生の可能性 | storage wrapperを作りtry/catchを統一 |
| 中 | `assets/audio/*.mp3` | BGM | 3MBから4.7MB程度の音源が複数 | 会場回線で初回再生が重くなる | 音源圧縮、必要時読み込み、短尺ループ化 |
| 中 | `assets/videos/story_endding.mp4` | Extra動画 | 約17MB | モバイル通信で重い | 圧縮版作成、poster表示維持、動画は任意DLにする |
| 中 | `assets/images/bg_mansion.jpg` | 画像 | 未参照の可能性がある大きい背景画像 | 公開対象に残ると容量増加 | 参照確認後に削除または `_unused` へ移動 |
| 中 | `assets/images/butterfly_gold.png` | 画像 | 参照が確認できない | 未使用なら容量増加 | 参照確認後に削除候補 |
| 中 | `style.css` | 見開き関連CSS | `room-visual-page` など未使用化した可能性 | CSSが肥大化 | 現表示確認後に未使用CSSを整理 |
| 中 | `script.js` | `pages` 配列 | データと描画ロジックが同一ファイル | 保守時に見通しが悪い | `pages.js` 等に分割。ただし静的構成は維持可能 |
| 中 | `script.js` | 署名ポーリング | 15秒ごとに全件取得 | 件数増加時に読み込み量増加 | Firebase SDKの購読、件数制限、ページングを検討 |
| 中 | `README.md` | Firebaseルール例 | ルール例のみ存在 | 実適用状態は確認不可 | Firebase Consoleの現在ルールを運用資料へ転記 |
| 低 | `index.html` | Google Fonts | 外部フォント読み込み | オフラインや低速回線で表示遅延 | font-displayやシステムフォント方針の検討 |
| 低 | `script.js` | 音声エラー | `catch` で握りつぶす箇所あり | 原因調査が難しい | 開発時のみconsole出力するフラグを追加 |
| 低 | ルート構成 | `package.json`なし | ビルド・lint・testコマンドなし | 品質確認が手動中心 | npm scripts導入を検討 |

## 未使用ファイルの可能性

以下はコード参照から未使用の可能性がある。削除前に実機表示と履歴確認が必要。

- `assets/images/bg_mansion.jpg`
- `assets/images/butterfly_gold.png`
- `assets/images/ornament_frame.png`
- `assets/audio/bk/` 配下
- `assets/images/bk/` 配下が存在する場合

## 到達不能な画面や処理

明確な到達不能画面は確認できない。ただし、`ending` typeのページが現在の `pages` 配列に存在するかは要確認。描画関数 `renderEndingPage` は残っているが、実データ上はエピローグが `story` typeで構成されている。

## 重複している処理

- 画面描画関数内で似た構造のHTML生成が複数存在
- Firebaseの保存・取得エラー処理が署名と抽選で個別実装
- CSSに過去の見開きレイアウト用スタイルが残っている可能性

## ハードコードされた値

- ページ本文、問題、正解、クレジット文言
- Firebase Realtime Database URL
- 外部リンクURL
- 音源・画像パス
- 署名最大件数、ポーリング間隔

## Firebaseの入力値検証不足

READMEにルール例はあるが、実際に適用されているかはリポジトリ内では確認できない。抽選データに対する `nickname` の型・最大長検証も運用ルール側で確認が必要。

## GitHub Pagesのベースパス問題

相対パスでアセットを参照しているため、`https://nekochanninaritai.github.io/blessing-melody/` 配下では動作しやすい。独自ドメインや別階層へ移す場合も基本的には問題ないが、キャッシュ対策のクエリ更新が必要な場合がある。

## 音声の自動再生制限への対応

音声開始ボタンがあり、ユーザー操作後に再生する実装。タブ非表示時の停止も実装されている。

## スマートフォン表示崩れの可能性

文章量、画像サイズ、アドレスバー表示差分により一部ページでスクロールが発生する可能性がある。`updatePageOverflow` による判定はあるが、実機確認が必要。
